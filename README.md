# Chronify

Chronify — навчальний планувальник задач на C#. Використовує .NET 10, Avalonia, SQLite та Entity Framework Core.

Особисті задачі зберігаються на ПК і доступні без інтернету та навчального сервера. Для першої реєстрації, роботи з групами й імпорту потрібен інтернет. Групи працюють через PostgreSQL у Neon, а отримані задачі зберігаються локально. Classroom і Notion потрібні лише під час імпорту.

## Запуск

Потрібен .NET 10 SDK. Команди виконуйте з кореня проєкту:

```powershell
dotnet restore
dotnet run --project modelforapp.csproj
```

Налаштування можна скопіювати з `.env.example` у `.env.local`. Якщо NeonSetup уже створив цей файл, залиште наявні дані підключення й додайте лише потрібні змінні Google. Налаштування Neon описане нижче.

Під час першого запуску створіть акаунт Chronify з підключенням до інтернету. Він зберігається в Neon і SQLite. Перший користувач отримує задачі й категорії зі старої версії бази, решта починають із порожнім списком.

Локальна база `chronify.db` лежить у робочій папці запуску. Вхід можна запам'ятати на цьому ПК.

## Що вміє програма

- Створювати, редагувати й видаляти задачі, починати та завершувати їх, повертати в роботу. Час завершення зберігається в `CompletedAt`. Закриті задачі не можна редагувати; дедлайн і тривалість перевіряються.
- Створювати, перейменовувати й видаляти категорії, задавати їм колір.
- Шукати під час введення та поєднувати фільтри за категорією, статусом, важливістю і строком. Кожен користувач може зберегти до п'яти фільтрів; повторна назва оновлює наявний.
- Сортувати задачі за EDF і динамічним пріоритетом, складати план на день, показувати перевантажені дні в календарі.
- Записувати робочі сесії вручну й порівнювати плановий час із фактичним.
- Показувати статистику за день, тиждень і місяць, підсумки за категоріями та відсоток вчасно виконаних задач.
- Використовувати один акаунт для локальної та спільної бази. В особистому кабінеті можна змінити ім'я й мову або вийти.
- Імпортувати вибрані чи всі задачі з Classroom і Notion, зберігати описи та вкладення Notion на ПК.
- Працювати з групами, кодами запрошення, чотирма ролями та призначенням задач. Завершення без інтернету стають у чергу на відправлення.

## Як влаштований проєкт

| Папка | Що містить |
|---|---|
| `Models` | Моделі даних і перевірки значень |
| `Repositories` | Читання й запис у SQLite, перевірки власника даних |
| `Services` | Пошук, планування, статистику та авторизацію |
| `ViewModels` | Стан екранів, команди й повідомлення користувачу |
| `Views` | Розмітку Avalonia, відкриття й закриття вікон, керування фокусом |
| `Data/Migrations` | Зміни структури локальної бази |
| `Tests` | Перевірки бази, алгоритмів, авторизації та інтерфейсу |
| `Chronify.Tests` | Тести xUnit для сортування, фільтрів, міграцій і моделей |
| `Shared` | Спільні об'єкти передачі даних (DTO) та правила ролей клієнта й сервера |
| `Tools/NeonSetup` | Початкове налаштування Neon і обмеженого доступу до бази |
| `Localization` | Словники трьох мов та оновлення перекладів |

Атрибут `[ObservableProperty]` із CommunityToolkit повідомляє про зміну властивості у ViewModel, і Avalonia оновлює екран. `[RelayCommand]` створює команду, яку можна прив'язати до кнопки. Списки на екранах використовують `ObservableCollection`.

## Мови інтерфейсу

В особистому кабінеті можна вибрати українську, російську або англійську мову. Відкриті екрани оновлюються одразу. Вибір зберігається для кожного акаунта в SQLite, у `UserPreferences.LanguageCode`, і відновлюється під час наступного входу.

Міграція `AddInterfaceLanguage` додає це налаштування без видалення даних. Для наявних акаунтів початкова мова — `ru`.

Переклади лежать у `RussianTexts.cs`, `UkrainianTexts.cs` та `EnglishTexts.cs`. У всіх трьох словниках мають бути однакові ключі. Зберігайте цілі фрази, а змінні значення передавайте через `Texts.Format`:

```csharp
string label = Texts.Get("Common.Save");
string message = Texts.Format("Import.Found", taskCount);
```

У XAML використовуйте прив'язку, яка оновлюється після зміни мови:

```xml
<TextBlock Text="{loc:Translate Common.Save}" />
```

Префікс `loc` задається як `xmlns:loc="using:Chronify.Localization"`. Щоб додати напис, додайте ключ із перекладом у всі три словники. Тести перевіряють ключі та відповідність параметрів `{0}`, `{1}` тощо.

Назви задач, категорій і груп, описи та коментарі користувача не перекладаються. Повідомлення PostgreSQL перекладає клієнт, тому змінювати спільну базу не потрібно.

## Алгоритми та статистика

### Сортування EDF

Спочатку застосовуються вибрані фільтри, потім задачі сортуються за найближчим дедлайном. Якщо дедлайн однаковий, вище буде важливіша задача. Задачі без дедлайну йдуть у кінці.

### Динамічний пріоритет

`Оцінка = важливість + терміновість + обсяг роботи`.

| Частина оцінки | Як рахується |
|---|---|
| Важливість | Числове значення `TaskPriority` × 25 |
| Терміновість | Прострочено — 100; до доби — 80; до трьох діб — 50; до тижня — 20; решта — 0 |
| Обсяг роботи | 1 бал за кожні 15 запланованих хвилин, не більше 40 |

Завершена задача завжди отримує 0. Це прості навчальні правила оцінки; їхні ваги зібрані в `DynamicPriorityCalculator`.

### План на день

Програма впорядковує задачі за динамічним пріоритетом і бере їх по черзі, якщо вони вміщуються в доступний час. Завелика задача пропускається, після неї перевіряється наступна. Завершені задачі та задачі без оцінки часу теж пропускаються.

Загальний час не перевищує введений ліміт. Такий підхід називається жадібним алгоритмом: він простий, але не гарантує найкращого заповнення часу.

### Статистика й календар

Період включає початкову дату й не включає кінцеву. Дані враховуються так:

- Активні та прострочені задачі — за дедлайном, а без дедлайну — за датою створення.
- Завершені задачі — за `CompletedAt`.
- Фактичний час — за датою робочої сесії `WorkSession`.

On-Time Rate — це частка вчасно завершених задач серед завершених задач із відомим дедлайном. Старі записи без `CompletedAt` у розрахунок не входять: для них невідомо, чи виконані вони вчасно.

Календар складає планові хвилини незавершених задач на кожну дату дедлайну. Якщо сума більша за особисту денну норму, день позначається червоним.

## Акаунти та вхід

Реєстрація одна: у звичайній формі входу. Спочатку акаунт створюється в Neon, потім його локальна копія та захищена сесія доступу зберігаються однією транзакцією SQLite. Без інтернету реєстрація не створить окремий локальний акаунт. Якщо запис у Neon вдався, а локальне збереження — ні, звичайний вхід відновить копію без повторної реєстрації.

Під час входу перевіряється пароль акаунта в Neon. На новому ПК створюється локальна копія з тим самим ID. Якщо мережа недоступна, раніше збережений користувач може увійти за локальним хешем пароля. Якщо Neon доступний і відхилив пароль, офлайн-вхід не застосовується.

Старий локальний акаунт переноситься під час звичайного входу після перевірки його пароля. Локальний ID і задачі залишаються, а зв'язок із загальним ID зберігається окремо. Самого збігу пошти недостатньо для доступу до старих даних.

### Паролі та сесії

- Локальні паролі зберігаються як хеш PBKDF2-HMAC-SHA256: 600 000 ітерацій та окрема випадкова сіль для кожного користувача.
- Хмарні паролі використовують pgcrypto/bcrypt. Довжина пароля — 8–72 байти UTF-8.
- У таблиці локальних сесій зберігається хеш випадкового токена. Сам токен для повторного входу захищений Windows DPAPI у файлі `chronify.session.bin`.
- Сесія діє 30 днів. Вихід відкликає її та видаляє локальний токен. Якщо DPAPI недоступний, вхід працює до закриття програми, а користувач бачить повідомлення, що сесію не збережено.
- Хмарна сесія зберігається в SQLite під захистом Windows DPAPI. Групи використовують її автоматично, без окремого входу.

Вихід прибирає локальні сесії доступу та відкликає токен Neon, якщо є мережа. Зв'язок між локальним і загальним акаунтом залишається для наступного входу. Сам файл SQLite не шифрується. Окремого перемикача акаунтів немає.

## Збереження даних і міграції

Міграції оновлюють структуру бази під час запуску. Перед оновленням наявної бази створюється копія `chronify.db.before-migration-*.db`. SQLite Backup API включає в неї також підтверджені записи з журналу WAL.

Старі міграції не змінюють. Для наступної зміни моделі додають нову міграцію та новий знімок схеми. Дані зберігаються в базі, а не в JSON-файлах.

## Імпорт із Classroom і Notion

В особистому кабінеті підключіть сервіс. Потім у меню «Добавить задачу» виберіть Classroom або Notion, курс чи таблицю або всі доступні джерела. Завантажте список і перенесіть вибрані задачі чи весь список.

`ExternalSourceInfo` зберігає джерело, зовнішній ID, посилання, стан і час синхронізації. Унікальне обмеження `(UserId, Provider, ExternalId)` захищає від дублікатів. Повторний імпорт пропускає наявні ID та зберігає зміни користувача. Прострочені задачі теж імпортуються.

Імпорт працює в один бік: зміни статусу в Chronify не змінюють здачу роботи в Classroom або запис у Notion.

### Google Classroom

1. Створіть проєкт у Google Cloud Console й увімкніть Google Classroom API.
2. Налаштуйте OAuth consent screen. Для тестового застосунку додайте пошти користувачів у Test users.
3. Створіть OAuth Client ID типу **Desktop app**. Введіть Client ID і Client secret у Chronify. Замість цього можна задати `CHRONIFY_GOOGLE_CLIENT_ID` та `CHRONIFY_GOOGLE_CLIENT_SECRET` у `.env.local` або середовищі запуску.
4. Натисніть «Подключить Google через браузер» й надайте доступ.

Офіційна бібліотека Google виконує OAuth із PKCE та локальним callback. Запитуються лише права `classroom.courses.readonly` і `classroom.coursework.me.readonly`: на активні курси студента й доступні йому завдання.

Токени та OAuth-реквізити зберігаються в SQLite окремо для кожного акаунта, зашифровані Windows DPAPI. Для публічного поширення Google може вимагати перевірку застосунку; навчальна організація теж може обмежувати доступ. Повний вхід у Google без реального OAuth-проєкту не перевірено.

### Notion

1. Створіть персональний токен Notion або внутрішнє підключення з правами читання.
2. Надайте доступ до таблиці Tasks і її сторінок.
3. Введіть токен у Chronify та натисніть «Подключить Notion».

Таблиця обирається зі списку доступних data sources. Назва задачі береться з колонки `title`, дедлайн — із першої заповненої колонки `date`. У навчальній таблиці варто залишити одну колонку дедлайну. Дата без часу означає кінець дня.

Програма читає сторінку з першої колонки разом із вкладеними блоками. Текст, списки, таблиці та код стають описом задачі. Файли, зображення й PDF із вмісту сторінки завантажуються в `TaskAttachments` як байти та доступні без тимчасових посилань Notion.

Ліміти вкладень: 20 МБ на файл, 50 МБ на задачу, 100 МБ на імпорт. Якщо вкладення не завантажилось або імпорт скасовано, неповні задачі не зберігаються. Колонки типу `files`, коментарі та вбудовані сторонні сервіси поки не імпортуються.

У списку «Все задачи» кнопка «Условия и вложения» відкриває локальний опис і файли. Звичайні вебпосилання, Google Drive та YouTube потребують інтернету. Файли Classroom у цій версії не копіюються з Google Drive.

## Групи та ролі

У розділі «Группы» створіть групу та передайте іншому учаснику код запрошення. Це окремий випадковий код, який бачить адміністратор, а не відкритий ID групи.

У базі `Groups` зберігає групи, `Members` — учасників і їхні ролі, `Assignments` — задачі з посиланнями на групу, автора призначення та виконавця. Списки ID не зберігаються в одній колонці.

| Роль | Що бачить | Кому може призначати задачі |
|---|---|---|
| Без ролі | Назву групи та очікування ролі | Нікому; отримувати задачі теж не може |
| Адміністратор | Усі задачі групи | Тимлідам і виконавцям |
| Тимлід | Усі задачі групи | Лише виконавцям |
| Виконавець | Лише свої задачі | Нікому |

Засновник — єдиний адміністратор групи. Новий учасник має стан «Без ролі» й не бачить задач та учасників, поки адміністратор не призначить йому роль. Особистими задачами він може користуватися одразу. Адміністратор може змінювати ролі інших учасників між виконавцем і тимлідом.

Автор призначення задає умови, дедлайн, важливість і початковий статус. Якщо статус «Новая», він сам запускає задачу кнопкою в групі. Виконавець завершує запущену задачу у своєму списку. Перевірки результату та повторного відкриття групової задачі поки немає.

Категорія призначеної задачі збігається з назвою групи. Її умови та категорію не можна змінити локально. Адміністратор і тимлід переглядають усі задачі в самій групі.

### Синхронізація та робота без інтернету

Дані груп зберігаються окремо для кожного локального акаунта в `CachedGroups`, `CachedMembers` і `CachedAssignments`. Призначені користувачу задачі також потрапляють у `Tasks` і враховуються в пошуку, плануванні та статистиці. Особисті задачі залишаються локальними й не надсилаються до груп.

Якщо завершити задачу без інтернету, результат і прапорець `PendingCompletion` зберігаються однією транзакцією SQLite. Наступне оновлення надсилає чергу. Повторне повідомлення про завершення сервер обробляє коректно. Для нових призначень, вступу та зміни ролей потрібен інтернет.

Синхронізація запускається при відкритті розділу «Групи» та кожні 5 секунд, поки він відкритий. Власник бачить нових учасників, учасники — зміни ролей і задач. Також є кнопка «Обновить группы / отправить результаты». Вибраний учасник і чернетка задачі зберігаються під час оновлення.

Закриття вікна скасовує фонові запити. Мережева помилка не видаляє кеш та локальні умови задач.

## Налаштування Neon

Програма підключається напряму: **Avalonia → PostgreSQL у Neon** через Npgsql. Окремий вебсервер, Render або localhost не потрібні.

Розробник налаштовує підключення через CLI:

```powershell
neon login
neon init -y --no-agent-setup --no-config --org-id <org> --project-id <project> --branch production
dotnet run --project Tools/NeonSetup/Chronify.NeonSetup.csproj
```

CLI прив'язує проєкт через `.neon` і записує `DATABASE_URL` у `.env.local`. NeonSetup використовує `DATABASE_URL_UNPOOLED` або `DATABASE_URL` власника. В одній транзакції утиліта створює схему `chronify` і SQL-користувача `chronify_client`, а його реквізити записує в `CHRONIFY_DATABASE_URL`. Повторний запуск зберігає пароль.

Схема та перевірки доступу лежать у `Data/Neon/schema.sql`. Для зміни наявних таблиць потрібні окремі SQL-оновлення: `CREATE TABLE IF NOT EXISTS` не змінює їхню структуру.

Застосунок використовує лише `CHRONIFY_DATABASE_URL`. Клієнтський SQL-користувач не має прямого доступу до читання чи зміни таблиць. Він викликає `chronify.request(token, action, payload)`, яка перевіряє сесію, членство, роль, автора призначення та виконавця. Знання клієнтського SQL-пароля чи зміна кнопок не дають доступу до чужих задач. Підключення перевіряє TLS-сертифікат.

JSON використовується для параметрів функції. Самі дані зберігаються у звичайних реляційних таблицях.

Файли `.env.local` і `.neon` виключені з Git. Для поширення програми покладіть біля exe окремий `.env.local` лише з `CHRONIFY_DATABASE_URL='...'`. Дані власника `DATABASE_URL`, `DATABASE_URL_UNPOOLED` та авторизацію CLI користувачам не передають. Учасники входять у Chronify зі своїми акаунтами; вхід у кабінет Neon їм не потрібен.

Перевірка підключення без зміни даних:

```powershell
dotnet run --project Tools/NeonSetup/Chronify.NeonSetup.csproj -- --inspect
```

## Перевірки

### Автоматичні тести

Модульні тести перевіряють `TaskSorter`, `TaskFilter`, `DurationText`, міграції, акаунти й режими сортування:

```powershell
dotnet test Chronify.Tests
```

Перевірки бази, алгоритмів, авторизації та інтерфейсу:

```powershell
dotnet run --project Tests/Chronify.Checks.csproj
```

Вони створюють бази й тестові акаунти в тимчасовій папці та не змінюють робочу базу. Для інтерфейсу використовується Avalonia.Headless. Знімки екранів зберігаються в `Tests/bin/Debug/net10.0/qa-*.png`.

GitHub Actions збирає програму й запускає xUnit на Linux, а сценарії Avalonia та DPAPI — на Windows. CI не потребує робочої бази. Перевірки справжнього Neon запускаються вручну:

```powershell
dotnet run --project Tests/Chronify.Checks.csproj -- --neon
```

Ця команда створює тимчасові хмарні акаунти та перевіряє чотири ролі, приватність, призначення задач, їх отримання в SQLite та надсилання завершень. У блоці `finally` видаляються лише створені перевіркою акаунти та їхні групи. Для очищення потрібен локальний `DATABASE_URL_UNPOOLED` власника.

Перевірки без `--neon` працюють без інтернету. Для перевірки справжніх Classroom і Notion потрібні ваші підключення.

### Прев'ю Avalonia у VS Code

Якщо розширення Avalonia 12.5 падає з `ReflectionTypeLoadException` для `Avalonia.Platform.Surfaces.IFramebufferPlatformSurface`, додайте в налаштування робочої папки:

```json
{
  "avalonia.preview.useLegacyPreviewer": true
}
```

Потім виконайте `Avalonia: Restart Previewer` у палітрі команд VS Code. Режим використовує хост із NuGet-пакета Avalonia проєкту (11.3.21). Це тимчасовий режим сумісності, позначений у розширенні як застарілий.

У режимі дизайну програма не запускає авторизацію, міграції та таймер оновлення задач.

### Що показати викладачу

Створіть два акаунти й перевірте, що їхні дані розділені. Додайте категорії та задачі, поєднайте фільтри й збережіть один із них. Складіть план на день, запишіть робочий час і перегляньте статистику. Змініть денну норму, щоб показати перевантаження в календарі.
