# Chronify

Навчальний планувальник задач на C# (.NET 10, Avalonia, SQLite, Entity Framework Core).
Програма працює локально без навчального сервера та без підключення до інтернету.
Групи працюють онлайн через PostgreSQL у Neon, отримані задачі зберігаються локально. Classroom і Notion потрібні лише під час імпорту.

## Запуск

Файл `.env.example` містить порожній шаблон налаштувань. Його можна скопіювати у `.env.local`.
Якщо NeonSetup уже створив `.env.local`, збережіть наявні реквізити й додайте лише потрібні змінні Google.

З кореня проєкту:

```powershell
dotnet restore
dotnet run --project modelforapp.csproj
```

Під час першого запуску потрібно створити обліковий запис Chronify при наявності інтернету. Він записується у Neon та SQLite. Перший користувач
отримує задачі та категорії зі старої версії БД. Нові користувачі починають із порожнім списком.
База `chronify.db` зберігається в робочій папці запуску. Вхід можна запам'ятати на цьому ПК.

## Структура проєкту

| Папка | Призначення |
|---|---|
| `Models` | Сутності та перевірки допустимих значень |
| `Repositories` | Читання і запис у SQLite; перевірка належності даних користувачу |
| `Services` | Алгоритми пошуку, планування, статистики й авторизації |
| `ViewModels` | Стан екранів, команди, повідомлення для користувача |
| `Views` | Розмітка Avalonia та дії з вікнами: фокус, відкриття, закриття |
| `Data/Migrations` | Послідовні версії схеми БД |
| `Tests` | Перевірки БД, алгоритмів, авторизації та інтерфейсу |
| `Chronify.Tests` | Модульні тести xUnit: сортування, фільтри, міграції та перевірки моделей |
| `Shared` | Спільні DTO та правила ієрархії ролей клієнта й сервера |
| `Tools/NeonSetup` | Початкове налаштування схеми та обмеженого доступу до Neon |

`[ObservableProperty]` з CommunityToolkit створює повідомлення про зміну властивості.
Завдяки цьому Avalonia оновлює елемент, коли змінюється значення у ViewModel.
`[RelayCommand]` створює команду для прив'язки кнопки. Колекції екранів використовують `ObservableCollection`.

## Реалізовані можливості

- Створення, редагування та видалення задач; початок, завершення й повернення в роботу.
- Час завершення `CompletedAt`, заборона редагування закритих задач, контроль дедлайну й тривалості.
- Категорії: створення, перейменування, видалення, кольорова мітка.
- Пошук під час введення та комбіновані фільтри категорії, статусу, важливості та строку.
- До п'яти збережених фільтрів для кожного користувача. Повторна назва оновлює існуючий фільтр.
- EDF, динамічний пріоритет, план на день, календар перевантаження.
- Ручне введення робочих сесій та порівняння запланованого й фактичного часу.
- Статистика за день, тиждень та місяць, відсоток виконання вчасно, підсумки за категоріями.
- Єдина реєстрація й вхід у загальну та локальну БД, особистий кабінет, зміна імені, вихід.
- Вибірковий або повний імпорт Classroom/Notion, локальні описи та вкладення Notion.
- Групи, коди запрошення, чотири ролі, делегування задач і локальна черга завершень.

## Як працюють алгоритми

### EDF

Спочатку йде найближчий дедлайн. За однакового дедлайну вище стоїть важливіша задача.
Задачі без дедлайну розташовуються в кінці. Комбіновані фільтри застосовуються до сортування.

### Динамічний пріоритет

`Оцінка = важливість + терміновість + обсяг роботи`.

- Важливість: числове значення `TaskPriority`, помножене на 25.
- Терміновість: прострочена задача — 100, до доби — 80, до трьох діб — 50, до тижня — 20, інші — 0.
- Обсяг: одна одиниця за кожні 15 запланованих хвилин, максимум 40.
- Завершена задача отримує 0.

Ваги — зрозуміла навчальна евристика. Вони знаходяться в одному класі `DynamicPriorityCalculator`.

### План на день

Задачі впорядковуються за динамічним пріоритетом. Далі жадібний алгоритм бере кожну задачу,
якщо вона вміщується в залишок доступного часу. Якщо задача завелика, перевіряється наступна.
Сума хвилин не перевищує введений ліміт. Задачі без оцінки часу й завершені задачі пропускаються.
Алгоритм легко пояснити; він не гарантує математично оптимальне заповнення часу.

### Статистика та навантаження

- Період задається напіввідкритим інтервалом: початок включно, кінець не включно.
- Активні й прострочені задачі враховуються за дедлайном; задачі без строку — за датою створення.
- Завершені задачі враховуються за `CompletedAt`.
- On-Time Rate: кількість вчасно завершених задач / кількість завершених задач із відомим дедлайном.
  Історичні записи без `CompletedAt` не дозволяють визначити вчасність і не входять у цей розрахунок.
- Фактичний час враховується за датою `WorkSession`.
- Календар підсумовує планові хвилини незавершених задач на кожну дату дедлайну.
  День стає червоним, коли сума перевищує особисту денну норму.

## Єдина авторизація

Пароль не записується відкритим текстом: використовується PBKDF2-HMAC-SHA256,
600 000 ітерацій та окрема випадкова сіль для кожного користувача.
У таблиці сесій зберігається хеш випадкового токена. Токен для повторного входу
захищається Windows DPAPI і записується у `chronify.session.bin`.
Термін сесії — 30 днів, вихід відкликає її та видаляє локальний токен.
Якщо DPAPI недоступний, вхід у поточному запуску працює, а програма показує повідомлення про незбережену сесію.

Реєстрація виконується один раз у звичайній формі входу. Спочатку створюється запис у Neon,
потім акаунт і захищена сесія доступу зберігаються однією транзакцією SQLite.
Без мережі реєстрація не створює лише локальний акаунт. Якщо Neon зберіг запис, але локальний
запис не вдався, звичайний вхід відновить локальну копію без повторної реєстрації.

Під час входу перевіряється пароль загального акаунта. На новому ПК автоматично створюється
локальна копія з тим самим ID. При мережевій помилці вже збережений користувач може увійти
за локальним хешем пароля; неправильний пароль у доступному Neon не вмикає офлайн-обхід.
Старий локальний акаунт переноситься при звичайному вході після перевірки його пароля:
локальний ID і задачі залишаються, відповідність загальному ID зберігається окремо.
Однакова пошта без підтвердження пароля не дає доступу до старих локальних даних.

Групи використовують отриману сесію автоматично: окремої реєстрації чи поля пароля там немає.
Вихід прибирає локальні сесії доступу та відкликає токен Neon, якщо мережа доступна.
Зв'язок ідентичностей залишається для наступного входу. Файл SQLite не шифрується.
Перемикач акаунтів та окремий інтерфейс мультиакаунта не додаються.

Джерела для реалізації: [PBKDF2 у .NET](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.rfc2898derivebytes.pbkdf2?view=net-10.0),
[рекомендації OWASP щодо паролів](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## Міграції та збереження даних

Міграції застосовуються під час старту. Перед оновленням існуючої БД створюється резервна копія
`chronify.db.before-migration-*.db`. SQLite Backup API включає також підтверджені записи з WAL.
Старі міграції не редагують: зміни моделі оформлюються наступною міграцією та новим знімком схеми.
JSON-файли для збереження даних не використовуються.

## Імпорт Classroom і Notion

`ExternalSourceInfo` містить джерело, зовнішній ID, посилання, стан і час синхронізації.
У БД є унікальне обмеження `(UserId, Provider, ExternalId)` для захисту від повторного імпорту.
У «Личный кабинет» є блок підключення сервісів. Після підключення меню «Добавить задачу»
дозволяє вибрати Classroom або Notion. Далі можна вибрати курс/таблицю або всі доступні джерела,
завантажити список і перенести вибрані задачі чи весь список. Повторний імпорт пропускає наявні
зовнішні ID і не перезаписує зміни користувача. Прострочені зовнішні задачі теж імпортуються.
Імпорт односпрямований: статус у Chronify не змінює здачу роботи в Classroom або запис у Notion.

### Налаштування Google Classroom

1. У Google Cloud Console створити проєкт, увімкнути Google Classroom API.
2. Налаштувати OAuth consent screen. Для тестового застосунку додати адреси користувачів у Test users.
3. Створити OAuth Client ID типу **Desktop app**. Скопіювати Client ID та Client secret у форму Chronify.
   Також можна задати `CHRONIFY_GOOGLE_CLIENT_ID` і `CHRONIFY_GOOGLE_CLIENT_SECRET` у `.env.local` або в середовищі запуску.
4. Натиснути «Подключить Google через браузер» та надати доступ.

Офіційна бібліотека Google виконує OAuth з PKCE та локальним callback. Запитуються лише
`classroom.courses.readonly` і `classroom.coursework.me.readonly`: активні курси студента й доступні йому завдання.
Токени та OAuth-реквізити зберігаються зашифрованими Windows DPAPI у SQLite, окремо для кожного акаунта.
Для публічного поширення Google може вимагати перевірку OAuth-застосунку; правила навчальної організації
також можуть обмежувати доступ. Без реального OAuth-проєкту наскрізний вхід у Google не перевірено.

### Налаштування Notion

1. Створити персональний токен Notion або внутрішнє підключення з правами читання.
2. Надати йому доступ до таблиці Tasks та її сторінок у Notion.
3. Ввести токен у Chronify й натиснути «Подключить Notion».

Таблиця обирається зі списку доступних data sources. Назва береться з колонки типу `title`,
дедлайн — з першої заповненої колонки типу `date` (у навчальній таблиці слід мати одну колонку дедлайну).
Дата без часу означає кінець дня. Сторінка, що відкривається з першої колонки, читається рекурсивно:
її текст, списки, таблиці та код стають описом задачі. Файли/зображення/PDF у вмісті сторінки
завантажуються та записуються байтами в `TaskAttachments`, тому тимчасові посилання Notion не потрібні
для повторного відкриття. Ліміти: 20 МБ на файл, 50 МБ на задачу, 100 МБ на один імпорт.
Якщо вкладення не завантажилось або імпорт скасовано, неповні задачі не зберігаються.
Окремі колонки Notion типу `files`, коментарі та вбудовані сторонні сервіси поки не імпортуються.

У списку «Все задачи» кнопка «Условия и вложения» відкриває повний локальний опис та файли.
Звичайні посилання на зовнішні сайти, а також посилання на матеріали Google Drive/YouTube потребують інтернету;
вони не є локально завантаженими вкладеннями. Файли з Classroom у цій версії не копіюються з Google Drive.

Джерела: [OAuth Google для desktop](https://developers.google.com/identity/protocols/oauth2/native-app),
[Classroom CourseWork](https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork/list),
[авторизація Notion](https://developers.notion.com/guides/authorization/overview),
[Notion data sources](https://developers.notion.com/reference/query-a-data-source).

## Групи та ролі

`Groups` містить групи, `Members` — зв'язок користувачів і груп з роллю,
`Assignments` — задачі з посиланням на групу, постановщика та виконавця.
Списки ID не записуються в одну колонку. Для вступу використовується окремий випадковий код,
а не відкритий ID групи. Код бачить її адміністратор.

| Роль | Видимість | Призначення задач |
|---|---|---|
| Без ролі | Тільки назва групи та очікування ролі | Не може отримувати або призначати задачі |
| Адміністратор | Усі задачі групи | Тимлідам та виконавцям |
| Тимлід | Усі задачі групи | Тільки виконавцям |
| Виконавець | Тільки свої задачі | Не може призначати |

Засновник групи — її єдиний адміністратор. Нові учасники мають стан «Без ролі» і не бачать задач та учасників групи до призначення ролі адміністратором. Особисті задачі це не блокує.
Адміністратор може змінювати ролі інших учасників між виконавцем і тимлідом.
Постановщик визначає умови, дедлайн, важливість і початковий статус. Якщо статус «Новая»,
саме він запускає задачу кнопкою у групі. Виконавець завершує вже запущену задачу
у своєму списку. Перевірку результату/повторне відкриття групової задачі поки не реалізовано.
Категорія дорівнює назві групи; умови та категорію призначеної задачі не можна змінювати локально.
Адміністратор і тимлід переглядають усі завдання безпосередньо у групі.

### Робота без інтернету

Після «Обновить группы / отправить результаты» серверна відповідь зберігається в
`CachedGroups`, `CachedMembers`, `CachedAssignments`. Кеш окремий для кожного локального акаунта.
Задачі, призначені цьому користувачу, також зберігаються у звичайній таблиці `Tasks` і беруть участь
у пошуку, плануванні та статистиці. Особисті задачі залишаються локальними й не надсилаються до груп.
Завершення без інтернету записується разом із прапорцем `PendingCompletion` в одній транзакції SQLite.
Наступне оновлення відправляє чергу; сервер допускає повторне повідомлення про завершення.
Мережева помилка не стирає локальні умови. Для нових призначень, вступу та зміни ролей потрібен інтернет.
Синхронізація запускається кнопкою, фонове опитування не використовується.

### Neon без окремого API

Схема роботи груп: **Avalonia → PostgreSQL у Neon**. Render, localhost та окремий вебсервер не потрібні.
Використовується Npgsql. Розробник отримує реквізити через CLI:

```powershell
neon login
neon init -y --no-agent-setup --no-config --org-id <org> --project-id <project> --branch production
dotnet run --project Tools/NeonSetup/Chronify.NeonSetup.csproj
```

CLI прив'язує проєкт через `.neon` і записує DATABASE_URL у `.env.local`.
Утиліта NeonSetup використовує DATABASE_URL_UNPOOLED або DATABASE_URL власника,
транзакційно створює схему `chronify` та SQL-користувача `chronify_client`.
Його реквізити записуються як CHRONIFY_DATABASE_URL. Повторний запуск зберігає пароль.
Схема й перевірки доступу знаходяться в `Data/Neon/schema.sql`.
Для зміни вже наявних таблиць потрібні наступні SQL-оновлення: CREATE TABLE IF NOT EXISTS
не змінює структуру існуючої таблиці.

Застосунок використовує **тільки CHRONIFY_DATABASE_URL**. SQL-користувач не має прав читання
або зміни таблиць: доступна функція `chronify.request(token, action, payload)`, яка перевіряє
сесію, членство, роль, постановщика та виконавця. Тому зміна кнопок чи знання клієнтського
SQL-пароля не відкривають чужі задачі. З'єднання перевіряє TLS-сертифікат.
Хмарні паролі зберігаються через pgcrypto/bcrypt (8–72 байта UTF-8), локальні — через PBKDF2.
Хмарна сесія захищена Windows DPAPI у SQLite. JSON використовується для параметрів функції,
а дані зберігаються у звичайних реляційних таблицях.

Після звичайного входу у Chronify відкрийте «Группы», створіть групу і передайте код іншому учаснику.
Новий учасник має стан «Без ролі», поки адміністратор не призначить виконавця або тимліда.
Операції з групами потребують інтернету, отримані задачі зберігаються на ПК.

Файли `.env.local` і `.neon` виключено з Git. Для розповсюдження біля exe створюється
окремий `.env.local` **тільки** з `CHRONIFY_DATABASE_URL='...'`. Реквізити власника
DATABASE_URL та DATABASE_URL_UNPOOLED і авторизація CLI користувачам не передаються.
Учасники входять у свої акаунти Chronify, а не у кабінет Neon.

Перевірка підключення без зміни даних:

```powershell
dotnet run --project Tools/NeonSetup/Chronify.NeonSetup.csproj -- --inspect
```

## Перевірки

### Прев'ю Avalonia у VS Code

Якщо розширення Avalonia 12.5 падає з `ReflectionTypeLoadException` для
`Avalonia.Platform.Surfaces.IFramebufferPlatformSurface`, увімкніть у налаштуваннях робочої папки:

```json
{
  "avalonia.preview.useLegacyPreviewer": true
}
```

Цей режим використовує хост із NuGet-пакета Avalonia поточного проєкту (11.3.21).
Після зміни виконайте команду `Avalonia: Restart Previewer` у палітрі команд VS Code.
Це тимчасовий режим сумісності: у розширенні він позначений застарілим.
Під час design mode програма не запускає авторизацію, міграції та таймер оновлення задач.

### Автоматичні перевірки

Модульні тести зберігають перевірки наявних `TaskSorter`, `TaskFilter` і `DurationText`
та доповнюють їх перевірками міграцій, облікових записів і нових режимів сортування.

```powershell
dotnet test Chronify.Tests
```

GitHub Actions збирає застосунок і запускає xUnit на Linux, а сценарії Avalonia та DPAPI — на Windows.
Перевірки справжньої Neon запускаються вручну; CI не потребує доступу до робочої БД.

```powershell
dotnet run --project Tests/Chronify.Checks.csproj
```

Перевірки створюють окремі БД та тестові акаунти в тимчасовій папці, не змінюючи робочу БД.
Для інтерфейсу використовується Avalonia.Headless. Знімки екранів зберігаються у `Tests/bin/Debug/net10.0/qa-*.png`.

Перевірка справжнього Neon і локального кешу:

```powershell
dotnet run --project Tests/Chronify.Checks.csproj -- --neon
```

Створює тимчасові хмарні акаунти й перевіряє чотири ролі, приватність, делегування,
отримання задач у SQLite та відправлення завершень. У finally видаляє тільки створені
цією перевіркою акаунти та їхні групи. Для очищення потрібен локальний DATABASE_URL_UNPOOLED власника.
Звичайні перевірки без --neon не потребують інтернету. Живі Classroom/Notion потребують ваших підключень.

Для демонстрації викладачу: створити два акаунти, перевірити розділення даних, додати категорії й задачі,
застосувати комбіновані фільтри, зберегти фільтр, сформувати денний план, записати робочий час,
переглянути статистику та змінити денну норму для перевірки календаря перевантаження.
